# OURSPACE V2.4.2 — Image Sharing Root Cause Analysis

## Executive Summary
Prior to release V2.4.2, image sharing across devices, browsers, and mobile networks failed intermittently or completely due to three critical architectural and code mismatches between client composers, Firebase Storage path resolution, and Firestore optimistic state synchronization.

---

## 1. Storage Category Mismatch
### Root Cause:
In `MessageInput.tsx`, both the camera photo upload and thumbnail upload called:
```typescript
uploadMediaToFirebaseStorage(space.id, 'images', file, ...)
```
However, `uploadMediaToFirebaseStorage` in `apps/web/src/lib/firebase/storage.ts` strictly accepted union type:
```typescript
category: 'image' | 'video' | 'document' | 'audio'
```
This discrepancy caused runtime path inconsistencies where files were sometimes saved under unmapped folders or generated conflicting Firebase Security Rules evaluations (`spaces/{spaceId}/{category}/{allFiles=**}`).

### Resolution:
- Implemented canonical category folder mapping (`getCategoryFolder(category)` and `normalizeMediaCategory(category)`) that cleanly maps both singular (`image`) and plural (`images`) to canonical folders:
  - `image` / `images` -> `spaces/{spaceId}/images/{userId}/{timestamp}_{fileId}`
  - `video` / `videos` -> `spaces/{spaceId}/videos/{userId}/{timestamp}_{fileId}`
  - `audio` -> `spaces/{spaceId}/audio/{userId}/{timestamp}_{fileId}`
  - `document` / `documents` -> `spaces/{spaceId}/documents/{userId}/{timestamp}_{fileId}`
- Updated all call sites in `MessageInput.tsx` to pass the canonical `'image'` category.

## 2. Attachment Metadata Inconsistency
### Root Cause:
The in-app camera modal produced dual assets: the full-resolution photograph and a downsampled thumbnail. When storing the message, `handleCameraPhotoConfirm` passed `thumbnail_url` and `thumbnail_path`. However:
1. `MessageAttachment` interface in `packages/types/src/index.ts` did not define `thumbnail_url`, `download_url`, or `storage_path`.
2. `useChatStore.ts` built `createdAttachment` by picking specific fields and omitted `thumbnail_url`, `download_url`, and `storage_path`, silently dropping them before writing to Firestore.

### Resolution:
- Extended `MessageAttachment` interface in `@ourspace/types` with:
  ```typescript
  thumbnail_url?: string | null;
  download_url?: string | null;
  storage_path?: string;
  ```
- Updated `useChatStore.ts` to map and persist `thumbnail_url`, `download_url`, and `storage_path`.
- Backwards compatibility is preserved by keeping `signed_url` and `file_path` as aliases.

---

## 3. Invalid Image Source Fallback (Raw Storage Path in `<img>`)
### Root Cause:
In `MessageBubble.tsx`, the image rendering component executed:
```typescript
const src = att.signed_url || att.file_path;
```
When `signed_url` was missing or expired, `src` fell back to `att.file_path`, which holds a relative Firebase Storage path such as:
```text
spaces/space-abc/images/user-xyz/1730000000_photo.jpg
```
The browser treated this string as a relative URL on the current website host (`https://ourspace-app-two.vercel.app/dashboard/chat/spaces/...`), resulting in an immediate HTTP 404 error and triggering `onError`, which crashed the image component into a permanent loading failure state.

### Resolution:
- Created `resolveMediaDownloadUrl(filePathOrUrl, fallbackUrl)` in `apps/web/src/lib/firebase/storage.ts`:
  1. If the input is already an HTTP(S) URL or Data URL, it is returned immediately.
  2. If the input is a Firebase Storage path (`spaces/...`), it checks an in-memory resolution cache.
  3. If un-cached, it retrieves the authorized Firebase Storage download URL via `getDownloadURL(ref(storage, path))`.
  4. Caches successful resolutions to prevent duplicate network calls.
- Updated `ImageAttachment` in `MessageBubble.tsx` to resolve URLs asynchronously with a loading skeleton, retry action with cache clearing (`clearMediaUrlCache`), rounded corners, full-screen zoom, and download options.
- Raw Storage paths are **never** passed to HTML `<img>` elements.

## 4. Message ID Discrepancy & Duplicate Bubbles
### Root Cause:
`useChatStore.ts` generated a local optimistic message ID (`msg-xxxxxxx`) and rendered the bubble. When syncing to Firestore, `sendMessageToFirestore` invoked `addDoc(msgsRef, payload)`, allowing Firestore to assign an entirely new autogenerated ID. When the realtime listener `onSnapshot` fired, it returned the message with the Firestore ID, causing duplicate bubbles, jitter, and broken message retry associations.

### Resolution:
- Replaced `addDoc` with `doc(msgsRef, message.id)` + `setDoc(docRef, payload, { merge: true })`.
- Generated stable message IDs format: `msg-<random>-<timestamp>`.
- Client-generated ID is 1:1 identical with the Firestore document key, ensuring strict idempotency and zero duplicate messages on retry.

---

## 5. Gallery Multi-Photo Staging and Error Recovery
### Root Cause:
`MessageInput.tsx` previously handled only a single file in state (`stagedMedia: StagedMedia | null`). If an upload failed, the staged photo was lost or replaced by an error string without an actionable retry button, forcing the user to re-navigate their photo gallery.

### Resolution:
- Refactored `stagedMedia` into `stagedMediaList: StagedMedia[]`.
- Added `multiple` attribute on `imageInputRef` and `fileInputRef`.
- Implemented a multi-photo preview tray showing thumbnail badges with individual remove options.
- Uploads items with cumulative progress bars.
- Staged items are retained in memory if sending fails, allowing the user to click "Retry" directly.
